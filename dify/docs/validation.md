```text

这位客人是老客，账本里有 2 笔未赎当票。
下一张当票编号：#3

与这次典当相关的旧账（引用时保留原文细节）：
- 当票 #1｜典当：第一次看海，码头有海风，回来买了桂花糕。想换一次好运。｜掌柜批注：海风咸，桂花糕甜，这段记忆我收了。当票拿好。
```

如果你在自己的实例里重新执行，按以下顺序操作。每一步都建议在 Dify「运行详情」里展开对应节点，截图留存。

1. **打开应用**：应看到开场白与三个建议问题。
2. **典当**：发送测试数据第 1 条。节点路径应为
   `开始 → 组装请求 → 是否查账(false) → 是否赎回(false) → 召回旧账 → 掌柜阿忘 → 封装本轮记账 → 记入账本 → 掌柜回复`。
   回答末尾应有 `—— 当票 #1 · 已记入忘川账本 ——`。
   截图点：`召回旧账` 的 body（第一次来、#1）、`记入账本` 的 body（`1`）。
3. **跨会话召回**：新开一个对话（不要换浏览器或隐身窗口），发送测试数据第 2 条。
   掌柜回答应先提到码头/桂花糕；`召回旧账` 节点 body 应包含「这位客人是老客」与当票 #1 原文。
   回答末尾应为当票 #2。
4. **查账**：发送 `查账`。节点路径应经过 `读取账本 → 账本回复`，回答列出 2 笔。
5. **赎回**：发送 `赎回 1`。节点路径应经过 `赎回当票 → 赎回回复`，回答返还 #1 原文并提示还剩 1 笔。
6. **复查**：再发送 `查账`，只应剩 #2。
7. **原始记忆（可选）**：若可访问 PowerContext 数据目录或 API，确认该玩家 scope 下有 3 条条目（2 条典当、1 条赎回），#1 为 `inactive`。

如果第 2 步的掌柜没有引用旧账，先检查 `召回旧账` 节点输出：有旧账文本说明召回成功，问题在 LLM 提示词或模型；没有旧账文本则检查玩家标识是否变化、输入是否包含旧账中的具体词。

## 8. 已知偏差与限制

- **真实 Dify 验收已完成**：上述截图来自真实 Dify 1.18 + 真实 DeepSeek 的 WebApp 会话，不是回放替身。图回放与后端验收作为补充证据继续保留。
- **模型幻觉风险**：掌柜 LLM 可能引用账本之外的细节。已通过三层缓解：系统提示词只许引用账本原文、`召回旧账` 注入账本与「记不清就别说」的指令、`去掉思考` 代码节点剥除 `<think>` 块。真实运行中空账本与赎回后场景均未再编造旧账。
- **LLM 替身**：回放中的掌柜回复是固定文本，只用于验证链路；真实掌柜语气由 Dify 的 LLM 节点产生。
- **词面检索**：最小部署不做语义扩展，输入需包含旧账中的具体词才能稳定命中。
- **单实例演示**：适配层没有鉴权与限流，不适合直接暴露到公网。
